# U01 bridge contract (schema 1)

## Ownership and lifecycle

`MainActivity` owns the existing authoritative `World`. `UnityBridge` is one process-level session router with a single `BridgeSession`; it keeps a weak activity reference and one world reference. It reuses the same session across rendering mode switches and configuration recreation, and rotates the session ID whenever a scenario, save, or completed turn replaces the world. Finishing the activity clears the session. The Java core remains the only place where commands can change rules and save data. Unity renders a detached copy of map ordinals and entity fields; Editor `U01_fixture.json` is generated from the real `coalition-190` Java scenario with seed 20260923 and is explicitly read-only.

Unity calls the Android Java static methods `UnityBridge.request(json)` and `UnityBridge.poll(sessionId)` through `AndroidJavaClass`. `request` validates and posts work to the Android main/logic thread, returning `QUEUED` immediately. `poll` only drains previously built immutable messages; it never queries `World` or constructs Unity objects. Native UI commands call `UnityBridge.changed(world)` after success. There is no game-rule implementation in C#, and no per-frame JNI entity query or map serialization. The Unity polling interval is 150 ms.

## Wire values

UTF-8 JSON strings over Android JNI. All field names are case sensitive. `schemaVersion=1`; `sessionId` is an opaque UUID string; `entityId` is a string such as `site:20004` or `unit:91`; `commandId` is an opaque string of at most 80 characters. Coordinates `q,r`, dimensions, owner, terrain ordinal, turn, officerId, troops, and other scalar game values are signed 32-bit integers. `sequence`, `revision`, and `clientSequence` are signed 64-bit integers, transported as JSON integers and parsed into C# `long` and Java `long` (never through a JavaScript Number). IDs and enum names remain strings, not hashes. Nullable or unavailable optional fields are omitted; `error` absent means successful receipt. Zero and -1 have their regular model meanings and do not stand for null.

`request` input: `{type:"snapshot",sessionId}` or `{type:"command",sessionId,commandId,clientSequence,revision,operation,cityId,officerId}`. Implemented operations call existing Java `World.patrol` and `World.recruit`; no standalone rules or AI. `poll` output: `{status:"OK",messages:[...],pending,dropped,commandCount,meanCommandMicros}` or `status:"STALE_SESSION"`.

Every message contains `type,sessionId,schemaVersion,sequence,revision,mapRevision,width,height,turn,player,entities,removed`. A full `snapshot` also contains `terrain`: exactly `width*height` characters in row-major order, `'A' + World.Terrain.ordinal()` for each cell. A `delta` includes changed entities and string IDs to remove. A successful domain `event` has `commandId,detail` (the confirmed Java result message). A `receipt` has `commandId` and optional `error`; rejected commands do not mutate the world. A `resync` message signals queue overflow. Terrain/map revision changes force a full snapshot; ordinary entity changes never resend the terrain. The current entity subset includes city/port/gate and unit IDs, kind, name, grid position, owner, troop count, energy/morale, officer, gold, food, and city order. Other visual entity kinds and detailed combat animation events are future work.

## Ordering and recovery

One session allocates monotonically increasing outgoing `sequence`. The Unity client rejects a missing sequence and requests a new snapshot. Snapshot resets its detached entity table; a delta upserts/removes IDs. An old session ID is rejected before queueing. The host checks `clientSequence` and expected `revision`, caches the last 256 command IDs and returns an idempotent receipt for retries. A stale or out-of-order command receives a failure receipt. A queue has at most 128 messages and a roughly 1 MiB in-memory budget; overflow drops backlog and emits `resync`. A new full snapshot deliberately clears older presentation messages. The transport request is capped at 4096 characters.

Only completed Java results produce events. The host's preexisting `SaveCodec` and RNG state are untouched by presentation. Real-scenario parity tests compare SHA-256 of full `SaveCodec.encode` output after direct vs bridge entry, covering stored RNG state. Editor fixture execution never changes Android state. `scripts/test-unity-u01.sh` covers Java parity, failure, deduplication, ordering, new session identity and overflow. `UnityBridgeInstrumentation` covers the Android Java entry on an installed APK; an actual C#→JNI run requires a built Unity Player and device and remains unverified.
